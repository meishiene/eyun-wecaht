# 迁移：用 Eyun 替换 AstrBot

更新于 2026-11-04。**这是方案，不是已完成的工作。** 下面标「未做」的都没有实现，也没有在真实环境里验证过。

## 结论
可以换，但不是改个配置。**知识库那一层（`kb_core.py`、网页、备份、种子脚本）不用动**；要新写的是「收发消息 + 调用大模型 + 指令分发」这一层，以及 Eyun 的发送、下载接口接入。Eyun 现有代码只做了「收」。

## 1. AstrBot 现在替我们做了什么（换掉它就要自己做）

插件 `astrbot/plugins/kb_digest/main.py` 里对 AstrBot 的调用次数（2026-11-04 统计）：

| AstrBot 提供的能力 | 插件里的用法 | Eyun 方案里对应 | 状态 |
|---|---|---|---|
| 收私聊消息（文字、图片） | `@filter.event_message_type`、`event.get_messages()`（各 1 处） | `eyun_recv.py` 已能收并存 SQLite；缺一个「读 SQLite → 变成缓冲区条目」的消费者 | 收：已有；消费：**未做** |
| 回复消息 | `event.plain_result` 54 处 | 需要接 Eyun 的发送文本接口 | **未做** |
| 回复文件（`/看` 发报告 .md） | `event.chain_result` + `Comp.File` 各 1 处 | 需要接 Eyun 的发送文件接口 | **未做** |
| 指令解析 | `@filter.command` 18 个、`@filter.regex` 1 个（白话） | 自己写路由：识别 `/` 前缀、按空格取参、保留「命令后必须有空格」的习惯 | **未做** |
| 调用大模型（含识图） | `context.get_using_provider()` 4 处、`provider.text_chat` 1 处 | `seed/llm.py` 有个带代理的同步 HTTP 客户端可参考；需改成异步、加图片输入 | **未做** |
| 图片落盘 | `comp.convert_to_file_path()` 1 处 | Eyun 回调只带缩略图和 XML，要用 `msg_id` + `content_xml` 调下载接口 | **未做** |
| 会话标识 | `event.unified_msg_origin` 6 处 | 换成 `chat_id`（私聊为对方 wxid；`eyun_recv.py` 的 `group_id` 列已按这个存） | 简单 |
| 平台名 | `event.get_platform_id()` 1 处（写进原文批次头） | 换成固定字符串 | 简单 |
| 阻止同一句话被重复处理 | `event.stop_event()` 2 处 | Eyun 没有默认聊天处理器，不需要；但「白话指令不当素材」的判断要保留 | 简单 |
| 进程与部署 | `docker-compose.yml`（AstrBot 容器） | 新写常驻服务 + 公网回调入口 | **未做** |
| 模型提供商配置 | AstrBot 管理页面 | 改成环境变量 | **未做** |

## 2. 不用改的部分
- `kb_core.py`、`nl_intent.py`：不依赖 AstrBot。
- `kb_web.py`：只读知识库目录，与机器人无关。
- `seed/`：自带模型客户端，与机器人无关。
- 测试：除 `test_plugin_flow.py`（它用桩模拟 AstrBot 事件）外都不用改。
- 备份脚本里写了插件所在路径；插件换位置后要同步改。

## 3. 建议的做法（尚未实施）

**第 0 步：先验证 Eyun 够不够稳。** 放弃的原因就是稳定性和封号风险。先用小号只收不回，连续观察一段时间（建议至少一周），确认不掉线、不被限制，再往下做。同时用控制台「保存并测试」的真实请求核对 `verify_sign` 的签名算法（目前是猜的）。

**第 1 步：把业务逻辑从 `main.py` 里拆出来。** 让它变成不依赖 AstrBot 的函数：输入（会话 ID、文字/图片列表、指令文本），输出（要回复的文本、可选文件）。AstrBot 版保留一层薄壳。这样两个机器人共用一份逻辑，可以并行跑，也不用担心改坏线上。`test_plugin_flow.py` 现有的桩可以改造成测业务层。

**第 2 步：写 Eyun 适配层。**
- 消费者：轮询 `messages` 表里 `chat_type='private'` 且 `is_self=0` 的新行，游标持久化。
- 发送：按 Eyun 官方文档实现发文本、发文件。
- 图片：用 `msg_id` + `content_xml` 下载。
- 防回环：机器人自己发的消息（`is_self=1`）不能当素材。

**第 3 步：模型客户端。** 异步封装，支持图片输入。`seed/llm.py` 是现成的参考（地址、模型名、代理）。

**第 4 步：部署。**
- 新增 systemd 服务（参考 `eyun/eyun-recv.service` 的加固写法）。
- 重新建回调的公网入口（之前用的隧道已撤掉）。
- 在 Eyun 控制台配回调地址和签名密钥；路径密钥用随机串。

**第 5 步：并行试运行。** AstrBot 不停，Eyun 先只收不回，对比一段时间的数据。

**第 6 步：切换与回滚。** 切换前先备份知识库（`systemctl start kb-backup.service`）。AstrBot 容器不要删，回滚就是把它重新启动。

**需要先确认：** Eyun 登录的微信号与 AstrBot 现在用的是不是同一个号；同一个号同时挂两套通道的行为**没有验证过**。

## 4. 换了之后能多出来什么
- **群消息入口。** Eyun 能收群消息，这是会议纪要里「群消息采集」的前提。但只是入口：把群消息变成知识库条目的管线、群与客户绑定，仍然要另外做（见 `功能归属与交接.md` 的 D 表）。
- **响应时长统计** 马上可用（`eyun/response_stats.py`，只统计群）。

## 5. 风险与不确定项
1. 非官方协议，有封号风险。
2. 稳定性：测试时实例当天掉线，掉线期间的消息收不到。迁移后需要掉线检测和告警，目前没有。
3. 签名算法未验证。
4. 发送、下载接口没有接入，本仓库也没有核对过它们的细节，工作量以接入时读文档为准。
5. 回调有 6 秒超时：`eyun_recv.py` 已按「先落盘再回 200、其余异步」设计，消费者不能放在回调里同步做。
6. 群消息全量留存涉及客户隐私，知识库的原文又是不脱敏的；纪要里也要求做数据安全评估。
7. `@11` 白话入口、「命令后必须有空格」「会改库的先确认」这些行为要在新路由里复刻。

## 6. 验收清单
- 私聊发文字/图片 → `/整理` → `/入库`，知识库多一条，内容与 AstrBot 版一致。
- `/看` 能收到报告文件；`/查`、`/树`、`/标签 树` 正常。
- `@11` 白话：查询直接执行，会改库的先复述、回「是」才执行。
- 重启后缓冲区不丢。
- 机器人自己的回复不会被当成素材。
- 掉线时有告警。
- 改造后的业务层测试全部通过。
